Lesson 0001 · 架构地图

jcode 架构地图：四层洋葱与两条运行路径

本课目标：在脑中建立 jcode 的仓库地图——任何功能属于哪一层、哪个 crate、动了它会影响谁。这是指挥 AI 修改代码、审核它提交的 diff 的共同前提。

1. 一张快照

jcode 是一个 Rust 写的终端 AI 编码代理（"harness"）：常驻守护进程 + 终端 UI，agent 负责循环调用大模型和执行工具。本仓库是上游 1jehuang/jcode 的 fork，当前 v0.76.0，约 7 千个提交。

事实数字
workspace 成员（crate）84 个：1 个根 crate + 83 个子 crateCargo.toml:9-93
语言Rust（edition 2024）+ TypeScript（telemetry-worker、SDK）+ Swift（ios）
谱系设计空间原点：pi（TypeScript）→ omp（pi 的 Rust 移植，见其 porting-from-pi-mono.md）→ jcode（同物种：Rust 终端 coding-agent harness）

2. 三个术语，先对齐

读 jcode 代码前只需要三个 Rust 工程术语，完整术语表在 glossary.html：

  • workspace：一个 Cargo.toml 管理的多 crate 项目集合（类比 Python monorepo）。
  • crate：编译单元，每个子目录 crates/jcode-* 就是一个 crate（类比 Python 发行包）。
  • module：crate 内的命名空间（类比 Python 模块）。

3. 四层洋葱（最重要的图）

84 个 crate 不是平铺的。核心是一条四层链，每一层用一行 pub use 把下一层整体再导出：

L1  jcode（根 crate，src/）            CLI、参数、子命令分发
        │  pub use jcode_tui::*;        src/lib.rs:22
L2  jcode-tui                        终端 UI、视频导出
        │  pub use jcode_app_core::*;  crates/jcode-tui/src/lib.rs:23
L3  jcode-app-core                    server、tool、agent（运行时上层）
        │  pub use jcode_base::*;      crates/jcode-app-core/src/lib.rs:24
L4  jcode-base                        provider、session、config、memory、prompt、bus

三个后果：

  1. 依赖只许向下：L1 可以依赖 L2/L3/L4，反过来不行。所以代码里到处是 crate::session、crate::config——真实定义在 L4，被逐层 re-export 上来。
  2. 这是编译期决策，不是审美：把最大的 rustc 编译单元拆开，「the largest compilation unit (and its peak memory) is roughly halved」jcode-base/src/lib.rs:6。仓库的拆分规范文档写得更细docs/CRATE_OWNERSHIP_BOUNDARIES.md。
  3. 其余 79 个 crate 是叶子，挂在不同层上：jcode-*-types（纯数据 DTO，禁止 IO/网络/进程，有脚本守卫依赖边界）、jcode-provider-*（各家模型适配）、jcode-tui-*（UI 组件）、基础设施（protocol/transport/sdk/harness-api…）。
Python 类比 每层 lib.rs 的 pub use jcode_xxx::* ≈ 每层 __init__.py 里写 from jcode_base import *——上层不用改 import 路径，下层模块自动可见。

4. 进程模型：两条运行路径

jcode 是客户端/服务端架构，但有一个高频例外：

路径 A（交互式，走 daemon）：
  TUI 客户端进程 ──NDJSON over Unix socket──▶ jcode serve（daemon）
  （每窗口一个进程）   Request/ServerEvent      持有全部 Session 和 Agent 实例

路径 B（jcode run，例外，不走 daemon）：
  同一进程内：Registry + Agent 跑一轮 → 打印结果 → 退出
  src/cli/commands.rs:2419 run_single_message_command

要点：

  • daemon 启动：客户端先探测 server_is_running()，没有就 spawn_server() 拉起src/cli/dispatch.rs:1024,1267。daemon 本体是 Server，会话表是 HashMap<String, Arc<Mutex<Agent>>>server.rs:651,664。
  • 线协议：换行分隔的 JSON（NDJSON），请求/事件枚举定义在 Request / ServerEventcrates/jcode-protocol/src/wire.rs:38,734；传输层在 jcode-transport（Unix socket / Windows 命名管道统一 API）。
  • 多窗口 = 多个客户端进程 subscribe 同一 daemon；没有 attach 子命令，attach 语义由 --resume <id> 承担。
  • jcode run、repl 在客户端进程内自建 agent，与 daemon 无关。给 AI 下指令时别说「改 attach 命令」或「让 run 走 daemon 会话」。

练习 A · 给任务归位（自查）

下面 5 个修改任务，先自己回答「动哪一层、哪个文件」，再展开答案核对。这是你以后给 AI 下指令时要做的事。

任务 1：给 agent 新增一个内置工具（比如天气查询）
L3 · crates/jcode-app-core/src/tool/ —— 新建文件实现 Tool trait，并在 tool/mod.rs:246 的 base_tools 里注册。
任务 2：接入一个新的模型服务商（比如 DeepSeek）
新建 crates/jcode-provider-deepseek-runtime/ + L4 的 jcode-base/src/provider/ —— runtime crate 实现 Provider trait，在 MultiProvider 装配处接入。
任务 3：新增一个 CLI 参数 --foo
L1 · src/cli/args.rs —— clap 的 Args/Command 定义，再在 dispatch.rs 处理分支。
任务 4：修改会话持久化格式（session 存储）
jcode-session-types（DTO）+ L4 · jcode-base/src/session.rs —— 数据结构在 types 叶子 crate，读写行为在 base。
任务 5：给 TUI 的工具执行状态换个显示样式
L2 · crates/jcode-tui/src/tui/ + jcode-tui-tool-display —— 表现层及其组件 crate，别去动 L3/L4。

练习 C · 动手验证地图（5 分钟）

打开下面三个文件，确认地图上的锚点真实存在。不用读懂全部代码，只需找到结构体定义那一行：

  1. crates/jcode-app-core/src/agent.rs → 找 pub struct Agent（:181）
